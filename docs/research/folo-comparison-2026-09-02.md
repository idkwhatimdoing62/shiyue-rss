# 拾阅与 Folo 对比（2026-09-02）

## 结论

拾阅不应复制 Folo 的 AI 时间线路线。两者更适合形成差异化：Folo 擅长统一时间线、开放网络发现和跨平台分发；拾阅应继续把“订阅 → 刷新 → 阅读 → 收藏/稍后读 → 找回”做成稳定的本地阅读工作流，并把资源库作为长期资产。

## 官方依据

- Folo README 将产品定位为把内容组织到一个时间线，并支持订阅源、精选列表、收藏整理和专注浏览：<https://github.com/RSSNext/Folo>
- Folo Actions 文档明确列出摘要、翻译、可读性全文、来源跳转、自动已读、屏蔽、重写规则和 Webhook：<https://github.com/RSSNext/Folo/wiki/Actions>
- Folo 官方 Feed Spec 的 Feed/Entry 模型包含描述、站点 URL、图片、TTL、ETag、错误时间、附件和媒体等字段，并支持 JSON Feed、RSS、Email、Webhook：<https://github.com/RSSNext/Folo/wiki/Folo-Flavored-Feed-Spec>
- Folo 官方发布记录持续修复时间线刷新、滚动已读、批量更新、图片/阅读模式和重复请求等问题，说明这些属于核心可靠性而非一次性 UI 打磨：<https://github.com/RSSNext/Folo/releases>
- Folo 官方没有足够文档证明现成的“稍后读”交互；公开 issue 反而提出过增加该功能的请求：<https://github.com/RSSNext/Folo/issues/938>

## 维度对比

| 维度 | Folo | 拾阅当前方向 |
| --- | --- | --- |
| 核心入口 | 统一时间线、精选列表、开放网络发现 | 总览首页、订阅列表、资源库、文章阅读 |
| 目标体验 | 快速筛选信息信号，AI 参与阅读 | 让人快速找到、打开、读完并找回内容 |
| 订阅模型 | Feed/Entry 元数据更丰富，协议覆盖更广 | 本地 Feed 生命周期明确，错误和刷新任务可观察 |
| 阅读状态 | 收藏、自动已读、屏蔽等规则丰富 | 收藏、稍后读、归档、已读相互独立，批量操作明确 |
| 正文 | 可读性模式和多媒体覆盖广 | 本地解析、图片缓存、异步图片定位修正，仍需继续压测 |
| AI | 产品主卖点：摘要、翻译、发现 | 可选增强；失败不阻断人用阅读闭环 |
| 长期资产 | 主要是时间线、收藏和 AI 上下文 | 独立资源库、用途/能力/证据和跨资料搜索 |
| 平台 | 官方提供桌面、移动和 Web 入口 | 当前以 Windows 本地桌面为主 |

## 对拾阅的取舍

### 应该学习

1. 把订阅源和文章的元数据做完整：站点标题、描述、站点 URL、图标、最近检查时间、错误状态和条件请求信息。
2. 把刷新、滚动、自动已读、图片加载当作可靠性系统，保留明确的任务状态和可重试入口。
3. 让列表承担快速扫描，正文承担专注阅读；常用动作尽量靠近当前上下文。

### 暂时不要复制

1. AI 时间线、开放网络推荐和社区发现；它们会扩大产品边界并稀释人用主路径。
2. 为了“看起来像 Folo”引入多平台同步或账户系统；这不是当前 Windows 本地优先目标。
3. 没有真实回归集就增加语义排序、自动规则或更多内容类型。

## 下一步优先级

1. **订阅列表切片**：左侧订阅源也采用固定行高和虚拟列表，增加 ↑/↓/Home/End/Enter 导航；失败信息放在行内状态，不另插一行，避免列表跳动。批量刷新、启用/暂停、删除应从选中集合一次提交。
2. **正文稳定性切片**：建立长文、图片慢加载、图片失败、刷新切换和恢复滚动位置的基准样本；验收指标是滚动帧时间、布局高度变化次数和阅读位置漂移，而不是主观“感觉不卡”。
3. **视觉收敛**：减少装饰性卡片和悬浮位移，固定标题/元数据层级与操作位置；先改善密度、对比度和焦点反馈，再考虑换图标或增加动效。

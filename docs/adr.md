## ADR-1 产品形态：阅读器 + 守护
- **背景**：既想在终端里读 RSS，又想后台盯着有新文章就提醒。
- **选择**：同时做 A（终端阅读器）和 C（常驻定时拉取 + 通知）。放弃纯导出工具形态。
- **后果**：范围较大；两个运行形态共享一份状态，存储成为骨架。

## ADR-2 阅读界面：全屏 TUI ~~（已被 ADR-13 取代，2026-07-13）~~
- **背景**：阅读界面可以是全屏 TUI、命令式子命令、或简单选单。
- **选择**：全屏 TUI，`ratatui` + `crossterm`。
- **后果**：体验最好；需写事件循环、三栏布局、焦点状态机——项目里较重的一块。
- **取代**：终端无法渲染图片（半块字符太糊），正文又多是 HTML，改用桌面 GUI（ADR-13）。TUI 与 `ratatui`/`crossterm` 依赖一并删除。

## ADR-3 存储：SQLite
- **背景**：daemon 与 TUI 是两个进程，并发读写同一份订阅/文章/已读状态。
- **选择**：SQLite（`rusqlite`），订阅源、文章、已读/星标全入库。
- **后果**：文件锁 + 事务兜住并发；去重、未读数、按源分组用 SQL 直接写。同步库，不拖入 async。

## ADR-4 守护模型：常驻进程
- **背景**：定时可交给系统调度器（任务计划程序/cron），也可自建常驻进程。
- **选择**：常驻进程 `rrss daemon`，内部循环按间隔抓取。
- **后果**：一命令即可运行，不依赖用户配置系统调度器；需自行处理自启/单例/崩溃（后续打磨）。
- **改写（ADR-14）**：`rrss daemon` 命令退役；那套"按每源 `next_fetch` 到期抓取"的调度循环抽成共享函数，改由 GUI 后台线程托管。调度*模型*保留，运行*载体*从独立进程变为 GUI 内的后台线程。`rrss update`（一次性抓一轮）保留。

## ADR-5 并发：异步 tokio + reqwest
- **背景**：定时并发抓取多个源；同步线程或 async 均可。
- **选择**：异步 tokio 运行时 + `reqwest`，并发用 `join_all`。
- **后果**：引入 async/await 与运行时；并发抓取顺手，契合练习 async 的目标。

## ADR-6 解析：feed-rs
- **背景**：源格式碎片（RSS 0.9x/1.0/2.0、Atom、JSON Feed）。
- **选择**：`feed-rs`，多格式归一成统一 `Feed`/`Entry` 模型。
- **后果**：入库逻辑只写一遍，不判格式；日期/相对链接/编码等细节交给库。

## ADR-7 通知：notify-rust（外部推送后做）
- **背景**：后台发现新文章后如何提醒。
- **选择**：先做 `notify-rust` 桌面 toast（N1）+ 日志兜底；外部推送（Telegram/邮件/webhook）列为后续扩展。
- **后果**：不用主动看终端也能收到提醒；推送渠道的凭据/重试等复杂度推迟。

## ADR-8 去重：guid/id 优先，DB 唯一约束
- **背景**：每轮重抓整源，须认出哪些已见，避免重复通知。
- **选择**：`entry_id` = guid/id，缺失回退 URL；`UNIQUE(feed_id, entry_id)` + `INSERT OR IGNORE`，用 `changes()` 得知新增数。
- **后果**：去重下沉到数据库，抓取逻辑无需先查再插，天然防并发重复插入。

## ADR-9 间隔：每源可覆盖 + 全局默认
- **背景**：不同源更新频率差异大。
- **选择**：`feeds.interval_secs` 可空覆盖全局默认；daemon 按每源 `next_fetch` 到期调度。
- **后果**：调度逻辑比单一全局间隔复杂（按到期检查、取最近到期 sleep）。

## ADR-10 OPML：不做
- **背景**：OPML 是订阅源通用交换格式。
- **选择**：暂不支持导入/导出，只 `rrss add <url>` 逐个加。
- **后果**：从其他阅读器迁移需手动加源；真需要时再引入 `opml` crate（增量小）。

## ADR-11 抓取失败：记录 + 退避 + 自动禁用
- **背景**：网络断、源挂、XML 坏，每轮都可能碰到。
- **选择**：失败写 `last_error`/`fail_count`；按 `2^fail_count` 指数退避（封顶）拉长下次抓取；连续失败超阈值自动 `disabled`，需手动 `enable` 恢复。每源抓取包在独立 `Result`，一个坏源不 panic 整轮。
- **后果**：坏源不拖垮整轮，也不无限重试死链；阈值可能误伤抽风源，可调。

## ADR-12 路径：directories + TOML + 标准目录
- **背景**：daemon 与 TUI 可能从不同工作目录启动，须指向同一库。
- **选择**：`directories` 定位系统标准目录——配置 `%APPDATA%\rrss\config\config.toml`，数据/日志 `%LOCALAPPDATA%\rrss\data\{rrss.db,rrss.log}`（Windows 下 directories 会自带 `config\`/`data\` 子层）。设置存 TOML 不进库。
- **后果**：双进程指向同一绝对路径；设置可用编辑器改，省一批 CLI 代码。

## ADR-13 阅读界面：桌面 GUI（取代 ADR-2）
- **背景**：RSS 正文本就是 HTML（含图片），终端渲染不了图片（半块字符太糊），HTML 也只能退化成纯文本。想要"看内容 + 看图"的阅读体验。
- **选择**：桌面 GUI，`egui`/`eframe`。渲染器选 **glow**（OpenGL），显式关掉默认的 wgpu 一大坨依赖树；`image` crate 禁 AVIF（不拉 `rav1e`）。图片下载/解码/缓存交给 `egui_extras` 的图片加载器。中文靠加载 Windows 自带字体（雅黑/黑体/宋体），否则 egui 默认字体是豆腐块。
- **后果**：图片清晰（真像素纹理，非终端半块）；HTML 能好好呈现。代价：引入 egui/eframe/egui_extras/image 一批 GUI 依赖，且是即时模式 UI，得自己管选中态/滚动/焦点。Windows-only（字体路径、`cmd /C start` 开浏览器）；跨平台另说。

## ADR-14 进程形态：全能单进程（GUI 内置抓取+调度）
- **背景**：抓取是异步（tokio+reqwest），egui 是主线程同步 UI 循环；且"新文章提醒"要常驻调度。要么 GUI 只当阅读器、抓取仍靠独立 daemon 进程，要么把抓取+调度收进 GUI 做成全能 app。
- **选择**：全能单进程。启动时 spawn 一个后台线程，内起 tokio 运行时，跑从 ADR-4 抽出来的共享调度循环（按每源 `next_fetch` 到期抓取写库）。UI 主线程保持同步、自己一个 DB 连接只读；两边靠同一 WAL 库 + `channel` 信号协调，后台抓完 `ctx.request_repaint()` 叫醒 UI。UI 自动刷新但不打断——实时更新未读数/列表，当前选中的源/文章按 id 保住不跳。`rrss daemon` 命令删除，`rrss update` 保留。
- **后果**：一个可执行文件既读又抓，不用另开 daemon。代价：进程内跨线程并发（两个 DB 连接、focused 标志、repaint 信号）比"两个进程各干各的"要小心；`rusqlite::Connection` 是 `Send` 非 `Sync`，故每线程各持一个连接。

## ADR-15 关窗行为：收到系统托盘
- **背景**：调度/通知只活在 GUI 进程里（ADR-14），关掉窗口就等于停调度、停提醒。想在没有可见窗口时也持续后台抓取+通知。
- **选择**：关窗不退出，缩到系统托盘（`tray-icon`，与同作者 rshot 一致）；托盘菜单才真退出（显示/隐藏 · 抓取一次 · 退出）。拦截 eframe 的关窗请求 → 改为隐藏窗口。通知复用 `notify-rust` toast，由后台调度器触发；窗口正聚焦时不打扰（后台线程读一个由 UI 维护的 focused 标志）。
- **后果**：像常驻后台的桌面 app，最小化/关窗都继续提醒。代价：多 `tray-icon` 依赖 + 托盘菜单/窗口显隐的事件接线；"彻底不开进程也想收通知"这个场景不再支持（那是已退役的 daemon 用例）。

## ADR-16 正文渲染：HTML→有序语义块
- **背景**：正文是 HTML，既要图文对位，又要保留标题、引用、代码、列表、图注、定义、表格和公式等阅读语义。
- **选择**：把 HTML 解析成有序 `Block` 序列。HTML5 DOM 负责忽略节点清理、标题与 `base href` 读取，并在进入流式解析前把 `picture/srcset` 归一为一个候选图片；`math/tex` 单独保留，`figcaption`、`dl/dt/dd` 和表格跨度进入专用模型；公式源交给内嵌 MathJax 在线程中生成 SVG，失败时退回源文本。图片按文章 URL 补全基址并由受限下载线程加载。
- **后果**：正文结构可测试、图文顺序稳定，复杂表格和公式不再只是纯文本近似。代价是语义模型和渲染器必须同步演进；远程图片仍有隐私与可用性成本，解析兼容性需要持续依赖真实站点 fixture 和视觉快照。

## ADR-17 产品命名：拾阅，并兼容旧数据目录
- **背景**：项目从内部代号 `rrss` 发展为可公开发布的软件，需要一个清晰的中文名称，同时早期测试版已经积累订阅、归档和摘录数据。
- **选择**：窗口、托盘、通知和正式发行名称统一为“拾阅”，命令与发行二进制使用 `shiyue`；继续读取旧 `rrss` 配置/数据目录，并保留旧 eframe app id。
- **后果**：公开品牌统一，已有用户升级后无需迁移数据或重设窗口状态。内部 crate 名和历史 ADR 中的 `rrss` 仍可保留，避免无价值的破坏性重命名。

## ADR-18 Windows 入口：GUI 与 CLI 双二进制
- **背景**：console 子系统可以保留 CLI 输出，但双击 GUI 会出现黑色命令行窗口；windows 子系统没有黑框，却无法可靠承载公开的命令行功能。
- **选择**：发行 `shiyue.exe` 与 `shiyue-cli.exe`。正式版 GUI 使用 Windows 子系统，CLI 继续使用 console 子系统；共享逻辑放入 library crate。GUI 启动外部链接时额外使用 `CREATE_NO_WINDOW`。
- **后果**：双击阅读器全程没有控制台窗口，CLI 输出和退出码仍然正常。发行包从单文件变为包含两个可执行文件的 ZIP。

## ADR-19 离线与数据治理：内容寻址缓存与可验证备份

- **背景**：文章图片来自不稳定 CDN，只保留内存纹理会让已收藏内容重新联网；直接复制正在使用的 WAL 数据库又可能得到不一致备份。用户还需要知道资料库占用、能安全清理，并能保护复制到外部介质的备份。
- **选择**：图片 URL 作为引用，字节按 SHA-256 放入 `image-cache/objects`，相同内容只存一次；URL 引用的修改时间作为最近使用信号，默认 1 GB 后淘汰并清扫无引用对象。数据库通过 SQLite online backup API 生成一致副本并做 `integrity_check` 与 `foreign_key_check`；恢复前必须先创建当前库安全副本，恢复和 `VACUUM` 期间暂停调度写入。普通备份之外，Windows 可用当前用户 DPAPI 生成 `.sybak`。
- **后果**：成功加载过的图片可离线显示，空间可预测；备份和恢复有可验证边界且具备回滚点。DPAPI 备份通常只能由同一 Windows 用户凭据解密，因此不能代替跨设备密钥管理；实时 `rrss.db` 仍是普通 SQLite，不能声称透明数据库加密。缓存和备份都是模块自有目录，清理操作不触碰文章、摘录或想法。
